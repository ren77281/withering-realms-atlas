# 博客文章 SEO 创作与优化规范

> 适用范围：本项目所有博客型游戏攻略、资料、对比和问答文章。创建新文章或大幅优化旧文章前必须读取；事实真实性和项目构建规则优先于任何关键词或篇幅目标。

## 1. 每篇文章的交付清单

开始写作前先明确并在工作结果中给出：

- 焦点关键词：1 个，对应一个主要搜索意图。
- 元标题：对应 frontmatter `title`。
- 元描述：对应 frontmatter `description`，不超过 150 个字符。
- 关键词组：焦点关键词 + 2–4 个长尾词，用于写作规划和自然布局。
- 事实来源：支撑文章关键结论的真实游戏体验、官网、Steam 或开发商资料。
- 内链计划：锚文本、目标 URL 和放置段落。
- 图片计划：英文文件名、ALT、插入位置和 AI 生图指令。

Google 不使用 `meta keywords` 作为排名信号，因此关键词组不输出成 `<meta name="keywords">`。可复用且符合现有词汇的主题词写入 frontmatter `tags`。

## 2. TDK 规则

### Title

推荐结构：`焦点关键词 + 核心价值 + 年份或 Latest`。

- frontmatter `title` 最长 80 个字符；同时确认最终页面标题没有因站点名拼接而失去可读性。
- 焦点关键词尽量靠前，但必须保持自然和点击价值。
- 只有内容确实具有时效性、已按当年资料核验并计划持续更新时，才使用年份或 `Latest`；禁止制造虚假新鲜度。
- 每页标题必须唯一，不能只替换少量词批量复制。

示例：`Withering Realms Release Date — Latest 2026 Updates`

### Meta Description

推荐结构：`覆盖内容 + 解决的搜索痛点 + 2–3 个核心价值点`。

- 40–150 个字符，简洁、可读，并准确对应正文。
- 自然出现一次焦点关键词或清晰近义表达，不堆砌。
- 不写正文没有兑现的承诺，不用空泛的“终极”“最佳”制造点击。

### Keywords

- 每篇只设 1 个焦点关键词和 2–4 个长尾词。
- 焦点关键词自然出现在标题、开头、至少一个 H2、摘要或结论中的合适位置；不要求机械重复。
- 长尾词分布在真正回答对应问题的 H2/H3 和正文中。
- 关键词密度不是验收指标；清楚完整地满足搜索意图才是验收标准。

## 3. 文章结构

默认使用：`痛点 → 拆解 → 解决方案 → 避坑 → 结论 + 延伸阅读`。

1. 开头用 100–150 个英文词直接描述读者痛点、给出结论范围，并说明本文能解决什么。
2. 正文从 H2 开始，不写 H1；H2/H3 保持清晰层级，标题尽量使用读者会搜索的问题表达。
3. 页面目录由 `ArticlePage` 根据 H2/H3 自动生成，不在 MDX 正文重复手写目录。
4. 分步操作放在 H3 下，写明前提、动作、结果和常见失败点。
5. 数据、案例和对比只能使用可追溯资料；无法核实则删除、标注边界或保持 `draft: true`。
6. FAQ 放 3–5 个真实常见问题，回答简短直接。FAQ 的目标是补全意图，不假设它一定获得 Google 富结果。
7. 结论总结核心答案，并使用描述性锚文本链接到真正相关的站内延伸阅读。

## 4. 图片 SEO 硬规则

### 数量

按正文字符数配置相关图片：

- 500–1000 字符：2–3 张。
- 1000–2000 字符：3–5 张。
- 2000 字符以上：至少 5 张。

图片必须有信息价值，不能用重复装饰图凑数量。若图片门槛与性能或事实真实性冲突，文章保持草稿并补足合格素材后再发布。

### 文件名和 ALT

- 文件名只用英文小写 `kebab-case`，例如 `withering-realms-release-timeline.webp`，不使用中文、空格或无意义编号。
- ALT 使用“焦点关键词 + 图片实际内容”的自然描述；焦点关键词在单条 ALT 中最多出现一次，不堆砌。
- 每张图的 ALT 必须描述该图本身，不能在不同图片间复制同一句话。
- 装饰性图片不承担关键词布局；没有内容价值的图片不要插入。

### 生成和插入

- 每张配图先写 AI 生图指令，包含主题、构图、信息重点、16:9、品牌色和禁止项，再生成并人工检查。
- AI 图只能作为编辑插图，不能伪装成官方游戏截图、实测数据或机制证据，也不能凭空创造游戏角色、地图和物品事实。
- 封面放在 `src/assets/covers/`，使用 1200×675，并通过 `pnpm gen-covers` 或等效流程生成；正文图放在 `public/images/articles/`，建议 16:9；gallery 图放在 `src/assets/gallery/`。
- 图片插在痛点解释、步骤、对比或结论前后的自然位置，不能连续堆放。
- 优先使用项目的 Astro Image 优化、WebP/AVIF、响应式尺寸和懒加载能力，新增图片后检查移动端布局与加载速度。

## 5. 内链与锚文本

- 只链接能继续解决当前读者问题的现有页面；创建链接前先确认目标 URL 实际存在。
- 锚文本应具体描述目标内容，例如 `Withering Realms PC system requirements`，不使用 `click here`、`read more` 等空泛文本。
- 不用完全相同的商业关键词大量重复锚文本；根据句子自然使用关键词、近义词或页面标题。
- 结论至少检查一次延伸阅读机会，同时在相关旧文章中评估是否应反向链接到新文章。

## 6. E-E-A-T 与白帽边界

- Experience：只能写真实体验或有来源的实测信息；没有体验时明确使用官方资料边界。
- Expertise：解释判断依据、适用版本、限制条件和玩家容易误解的地方。
- Authoritativeness：使用已配置作者信息、真实来源和相关站内主题集群建立权威性。
- Trust：维护发布日期、`lastModified`、作者、来源、HTTPS、法律页面和更正记录。
- 禁止关键词堆砌、隐藏文本、伪造评论、批量同义改写、购买垃圾外链和制造虚假年份新鲜度。

## 7. Schema 与技术 SEO

- Article、BreadcrumbList、ImageObject、VideoObject 等 JSON-LD 已由模板根据 frontmatter 自动生成，不在文章正文重复手写 Schema。
- FAQ 内容写在正文中；只有项目现有结构明确支持且数据真实时，才使用相应结构化字段。
- 每篇文章必须有唯一 canonical、可索引状态、正确 sitemap URL 和可访问的内链。
- 保持移动端可读性和速度；图片数量增加时重点检查 CLS、LCP、图片尺寸和懒加载。

## 8. 发布前验证

1. 逐条核对焦点关键词、Title、Description、长尾词、来源、内链和图片计划是否兑现。
2. 肉眼检查正文层级、移动端布局、图片相关性、ALT 和所有锚文本目标。
3. 运行 `pnpm check-content && pnpm build`。
4. 涉及链接变化时运行 `pnpm check-links`。
5. 检查构建后的 Title、Meta Description、canonical 和 JSON-LD，避免重复或缺失。
6. 未通过事实、图片或技术验收的文章保持 `draft: true`，不得为了数量直接发布。
