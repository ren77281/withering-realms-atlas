# Withering Realms 站点运营与执行基线

> 本文是本 fork 的站点级约束。所有选题、内容、SEO、统计、广告、部署和多站扩展操作，都必须先按本文判断当前阶段，再查对应手册章节执行。

## 1. 规则来源与优先级

1. 根目录 `AGENTS.md`：工程硬约束和 Agent 自动执行规则。
2. 本文：Withering Realms 当前阶段、推进顺序和站点级门禁。
3. `docs/handbook/zh/`：仓库内学习手册的具体命令与操作步骤。
4. `docs/content-format.md`、`docs/sourcing.md`、`docs/deployment.md`、`docs/seo.md`、`docs/ads.md` 等专题文档：执行某一步时的详细规范。
5. 在线最新版学习手册：`https://anvilwiki.pages.dev/zh/landing/docs/learn/`。在线手册出现新规则时先与当前仓库版本比较；命令以当前仓库实际支持为准。

Google、Cloudflare、广告平台、税务、价格、审核门槛等外部规则会变化。涉及第三方配置、付费或申请前，必须重新核验对应官方资料，不能把手册中的示例数字当作长期事实。

## 2. 必须遵守的 11 阶段顺序

1. 选游戏：评分达到 60 分，至少两个独立人气来源，检查搜索结果竞争；最多两天做决定。
2. 工具准备：安装并验证 Node、pnpm、Git 和本地开发环境。
3. 初始化站点：Fork、应用模板、替换游戏配置并本地启动。
4. 首批内容：发布 10–15 篇经过核实的核心页面。
5. 正式上线：通过 GitHub 和 Cloudflare Pages 部署到自有域名。
6. Google 收录：接入 GSC、提交 sitemap，优先处理重点 URL。
7. 统计与广告：先接入统计；达到内容、合规和质量门槛后再申请广告。
8. 每周运营：根据搜索数据更新、补充和淘汰内容，修复体验问题。
9. 模板化：第一站运营节奏稳定后，检查代码纯净度并形成换皮清单。
10. 批量页面：仅把已验证的内容模式批量生成成草稿，逐篇核实后分批发布。
11. SEO 进阶：每页承接一个主要搜索意图，持续优化内链、外链和内容满足度。

当前已经有 Lootbound 与 Withering Realms 两个站点。不得跳过前置门禁，直接用广告、批量页面或第三站代替现有站点的流量验证。

## 3. 内容与 SEO 硬规则

- 游戏事实只能来自真实体验、游戏官方页面、Steam、开发商公告或其他可追溯可靠来源。
- 禁止编造兑换码、数值、掉率、角色能力、地图信息、发布日期或平台支持情况。
- 未核实内容保持 `draft: true`；草稿必须逐篇核对、逐篇肉眼验收，不能一次批量翻正。
- 一个页面只承接一个主要搜索词或搜索意图，避免多个页面互相争夺同一关键词。
- “兑换码优先”等手册内容是特定游戏的示例。Withering Realms 没有可靠对应需求时，不为套模板硬建栏目。
- 内容数量不是目标。只补充有真实玩家需求、可靠来源并能比现有搜索结果更好解决问题的页面。
- 所有新文章和大幅优化必须遵循 `docs/blog-seo-authoring.md` 的 TDK、结构、图片、内链、E-E-A-T 与发布验收规则。
- 创建或修改文章前，必须读取 `docs/content-format.md`、`src/content.config.ts`、`src/config/navigation.ts` 和同类现有文章。
- 文章完成至少运行 `pnpm check-content && pnpm build`；构建后涉及链接变化时再运行 `pnpm check-links`。

## 4. 部署、统计与变现门禁

- 当前仓库保留 `wrangler.toml`，因此它是 Cloudflare Pages 构建变量的唯一真相源；不要只改 Cloudflare Dashboard 变量。
- 推送生产改动后，必须等待 Cloudflare 部署进入终态，并在线验证受影响页面。Git push 成功不等于上线完成。
- 新站优先使用 Cloudflare Web Analytics 和 Microsoft Clarity；GA4 仅在确有额外分析需求时启用。
- AdSense 是变现手段，不是起量手段。申请前至少应有自有域名、约 15–20 篇真实内容、必要法律页面且无死链；实际申请时重新核验官方政策。
- 新增下一站（当前即第三站）前，至少一个现有站点必须形成稳定的每周运营节奏，并同时满足：
  - `pnpm template-audit` 没有 `❌`；
  - 已形成 `docs/rebrand-checklist.md`；
  - 代码层不含 Withering Realms 专属内容。

## 6. 当前优化目标（首个 28 天周期）

目标周期：2026-08-26 至 2026-09-23。以下是根据当前 14 篇已发布文章制定的首轮验证目标，不是流量承诺。`anvil-ops doctor` 当前确认站点配置正常，但 GSC 与 Cloudflare API 凭据尚未接入自动报表，因此第一份人工或 API 报告产生后，应以真实基线修订目标。

### 核心结果指标

| 指标 | 定义 | 14 天目标 | 28 天目标 | 数据源 |
|---|---|---:|---:|---|
| 可索引内容收录率 | GSC 已收录内容 URL ÷ sitemap 中可索引内容 URL | ≥70%（当前 14 篇即至少 10 篇） | ≥85%（至少 12 篇） | GSC 页面索引报告 |
| 搜索激活页面数 | 获得 Google 自然搜索曝光或点击的内容页数量 | 至少 5 篇获得曝光 | 至少 3 篇获得点击 | GSC 页面报告 |
| 长尾查询进入前 20 数量 | 平均排名 1–20 的目标长尾查询数量 | 建立首个真实基线 | 至少 5 个 | GSC 查询报告 |

这些目标用于判断站点是否开始被 Google 理解和分发。若游戏本身搜索需求不足，必须区分“页面质量问题”和“市场没有需求”，不能用批量增加页面掩盖需求不足。

### 可控驱动指标

- 在首轮周期内完成现有 14 篇文章的 SEO 审计：每篇只有一个焦点关键词、2–4 个长尾词，并核对 Title、Description、来源、图片、ALT、内链和搜索意图。
- 每周固定记录一次 GSC、Cloudflare Web Analytics 和 Clarity 数据，只处理证据最强的前三项机会。
- 只有发现真实搜索缺口且具备可靠来源时，才在本周期新增 2–4 篇页面；文章数本身不作为成功指标。
- 优先优化有曝光但 CTR 低、平均排名 8–20、或用户行为显示未解决问题的页面。

### 质量护栏

- 未核实内容发布数必须为 0；所有未完成页面保持 `draft: true`。
- `pnpm check-content`、`pnpm build` 和适用时的 `pnpm check-links` 必须通过。
- 不允许关键词互相争夺、批量同义改写、重复模板正文或为达到页数制造不存在的游戏实体。
- 不以牺牲移动端速度、CLS/LCP、可读性或事实可信度换取图片数和页面数。

### 程序化 SEO 扩量门禁

Task Bar Hero 案例证明的是“真实结构化游戏数据 + 实体关系 + 多语言”的程序化 SEO，不是普通博客批量改标题。对 Lootbound 和 Withering Realms，先完成实体数据盘点；只有同时满足以下条件才启动扩量试点：

1. 存在可持续核验的数据来源，并能识别至少 50 个真实独立实体；
2. 每个实体页都有独有属性、用途、来源、掉落、制作或关联关系，而不是只有名称不同；
3. 先发布 20–50 个页面的小批量试点，逐页可访问、可索引且内部链接完整；
4. 试点运行 28 天后，收录率达到 70%，至少 20% 的页面获得搜索曝光，且没有薄内容或重复内容问题，才继续扩大。

若门禁未通过，先优化数据质量和页面价值，不生成数千或数万页面。

## 7. Agent 执行约定

- 不为本站日常工作开启持久 Goal。
- 可恢复、低风险、顺序明确的步骤连续执行，不因普通小问题反复询问。
- 仅在登录、验证码、付费、不可逆操作，或会显著改变选题、部署、变现和多站范围的关键决策前暂停。
- GitHub 常规授权操作可以继续；未经用户要求不做 force push，也不覆盖用户未提交改动。
- 每次工作先判断所在阶段，结束时给出实际验证结果和仍未满足的下一道门禁。
